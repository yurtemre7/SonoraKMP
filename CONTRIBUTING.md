# Contributing to Sonora

Thanks for helping out! This guide covers commits, pull requests, local checks, localization and releases.

## Commit messages

We use [Conventional Commits](https://www.conventionalcommits.org). Release notes and `CHANGELOG.md`
are generated from commit subjects by [git-cliff](https://git-cliff.org) (`cliff.toml`), so the subject
is what users read.

```
<type>(<optional scope>)<optional !>: <subject>
```

| Type       | Use for                                   | Release notes section |
|------------|-------------------------------------------|-----------------------|
| `feat`     | A new user-facing feature                 | Features              |
| `fix`      | A bug fix                                 | Fixes                 |
| `perf`     | A performance improvement                 | Performance           |
| `refactor` | Code change with no behavior change       | Refactoring           |
| `docs`     | Documentation only                        | Documentation         |
| `build`    | Gradle, dependencies, tooling             | Build & CI            |
| `ci`       | GitHub Actions workflows                  | Build & CI            |
| `test`     | Adding or fixing tests                    | Tests                 |
| `chore`    | Anything else (also `style`, `revert`)    | Chores                |

Rules:

- Subject in the imperative mood ("add", not "added"), lowercase, no trailing period, at most 72 characters.
- Scope is optional and names the area: `player`, `library`, `settings`, `l10n`, `shared`, ...
- Add `!` after the type/scope for a breaking change (e.g. dropped setting, migrated data).
- Keep bodies short or omit them; put the reasoning in the PR description.
- `release:` commits and merge commits are left out of the notes.

Examples:

```
feat(player): add sleep timer
fix(library): keep sort order after rescan
perf: cache decoded album art
refactor(shared)!: rename playlist storage keys
docs: explain release process
build: update media3 to 1.9.0
ci: upload lint reports
```

## Branches and pull requests

1. Branch off `main` (`feat/sleep-timer`, `fix/rescan-order`, ...).
2. Keep each PR focused on one change; split unrelated work.
3. Run the local checks below before pushing.
4. Open a PR against `main`. CI runs lint, unit tests and a debug build; it must be green.
5. PRs are squash-merged, so the PR title must itself be a valid Conventional Commit subject.

## Running checks locally

Requires JDK 17+ and the Android SDK (the Gradle wrapper handles the rest).

```sh
./gradlew lintDebug              # Android lint (fails on errors)
./gradlew testDebugUnitTest      # unit tests
./gradlew assembleDebug          # debug APK -> androidApp/build/outputs/apk/debug/
./gradlew lintDebug testDebugUnitTest assembleDebug   # everything CI runs
```

Debug builds install next to release builds (`.dev` application ID, "Sonora Dev" label).

## Localization

Sonora ships in English and Japanese. **No hardcoded user-visible strings** in Kotlin or XML:
every label, message, content description and notification text goes through string resources.

To add a string:

1. Add it to `androidApp/src/main/res/values/strings.xml` (English, the default):
   ```xml
   <string name="settings_sleep_timer">Sleep timer</string>
   ```
2. Add the same key to `androidApp/src/main/res/values-ja/strings.xml`:
   ```xml
   <string name="settings_sleep_timer">スリープタイマー</string>
   ```
3. Use it via `stringResource(R.string.settings_sleep_timer)` in Compose or `context.getString(...)` elsewhere.
   Use `<plurals>` for counts and placeholders (`%1$s`, `%1$d`) instead of string concatenation.

Name keys `area_purpose` in snake_case. If you can't write the Japanese text, say so in the PR so a
translation can be added before merging; both files must contain the same keys.

## Releases

Never bump versions by hand. A release is a commit on `main` whose subject is `release: <version>`:

```sh
git commit --allow-empty -m "release: 1.4.0"    # or "release: 1.4.0-beta.1" for a pre-release
git push origin main
```

The **Release** workflow sees the `release:` subject, runs the unit tests, builds a signed APK and
AAB with `-Psonora.versionName=1.4.0`, creates the tag `v1.4.0`, and publishes a GitHub release with
`sonora-1.4.0.apk`, `sonora-1.4.0.apk.sha256` and `sonora-1.4.0.aab`, plus notes generated by
git-cliff since the previous `v*` tag. Versions containing `-` are marked as pre-releases. Pushing
a version whose tag already exists fails. Other pushes to `main` don't release anything.

### Nightly builds

The **Nightly** workflow builds `main` every night at 03:17 UTC (skipped if nothing changed) and
replaces the rolling **nightly** pre-release with `sonora-<next>-nightly.<date>.apk` and its
checksum. Nightlies are signed with the release key, so they install over a release, and they are
never offered by the in-app updater. Run it by hand from **Actions → Nightly** (tick `force` to
rebuild an unchanged `main`).

`versionCode` is derived from the version name in `androidApp/build.gradle.kts`:

```
versionCode = (major * 1_000_000 + minor * 1_000 + patch) * 10 + stage
stage: final = 9, alpha.N = 0..2, beta.N = 3..5, rc.N = 6..8   (N = 1 is the first slot, clamped)
```

So `1.4.0` → `10040009`, `1.4.0-beta.1` → `10040003`; pre-releases always sort below their final
release. Minor and patch must stay below 1000. Pass `-Psonora.versionCode=N` to override.

To validate a release without publishing, run the Release workflow manually (**Actions → Release →
Run workflow**) with `dry_run` checked and a `version`; the APK, AAB, checksum and notes are uploaded
as workflow artifacts (debug-signed if signing secrets are unavailable).

Preview the notes locally with `git cliff --unreleased --tag v1.4.0`, or regenerate the full
changelog with `git cliff -o CHANGELOG.md`.

### Signing secrets (maintainers)

Release builds need these repository secrets:

| Secret                     | Value                                         |
|----------------------------|-----------------------------------------------|
| `SONORA_KEYSTORE_BASE64`   | `base64 -i release.jks` output                |
| `SONORA_KEYSTORE_PASSWORD` | Keystore password                             |
| `SONORA_KEY_ALIAS`         | Key alias                                     |
| `SONORA_KEY_PASSWORD`      | Key password                                  |

Locally, put the same values in an untracked `keystore.properties` (`storeFile`, `storePassword`,
`keyAlias`, `keyPassword`); without it release builds fall back to debug signing.
